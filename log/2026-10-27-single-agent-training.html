单 Agent 训练：一步一步看懂今天那篇文章

今天发的文章《多 Agent 祛魅：为什么“单 Agent + Skill”才是一人公司的最优解？》的逐节拆解。
默认你什么都不知道。每个词第一次出现，都会讲清楚它是什么、像什么、为什么重要。

2026-10-27 · 对应文章 10 节 · 按顺序读，每课约 3 分钟

怎么用这页：从第 0 课按顺序读到第 10 课。读完能回答文末三道自测题，就算看懂了今天的文章。读的时候不用记代码，不用记英文缩写——记住每课那句人话就够了。

第 0 课 · 先认识四样东西

没有这四样东西，后面全是黑话。先把地基打好。

对应知识点

  • 电脑：一台按指令干活的机器。你给它指令，它照做，不问为什么。
  • 程序：写给电脑的指令清单。像菜谱：先放什么、后放什么、火开多大，一步一步写清楚。
  • 大模型：一种特别的程序。你说一句人话，它回一句人话。它很会说话，但有三个短板：不记事，不动手，关掉窗口就忘。
  • 聊天和干活的区别：聊天是问一句、答一句。干活是交代一件事，对方多轮做完，中间不用你一步步指挥。今天这篇文章讲的，就是怎么让大模型从“聊天”变成“干活”。

第 1 课 · 为什么多 Agent 会变坏（对应文章开头 + 01 节）

文章开头在说：过去两年最流行画很多 Agent 分工图，看起来很厉害；现在发现，分工本身成了最大的累赘。

对应知识点

  • Agent（智能体）：能自己多轮干活的模型。不是一个新东西，是“模型 + 循环 + 工具”凑出来的工作方式（第 2 课细讲）。
  • 组织图和康威定律：你怎么分工，系统就长成什么样。公司里每个部门各配一个专属 Agent，最后攒出几百个功能重叠的 Agent，谁也不服谁，也没有统一标准。
  • 上下文：模型一次能记住的工作台面。台面就这么大，东西一多就乱，旧东西就被挤掉。
  • 电话游戏：Agent 之间传话，每传一次丢一点细节。像小时候玩的传话游戏，传到最后面目全非，而且没人知道丢的是哪一句。
  • 科学怪人提示词：每个人都往指令里加一句话，最后指令自己打架，语气精神分裂。名字来自科学怪人——东拼西凑缝出来的东西。
  • 交接成本：每次换手，都要重新讲一遍背景。又慢，又贵，又丢东西。这是全文最核心的一个词，后面反复出现。
和你的关系：你指挥我的时候，如果让我拆成五六个 Agent 各干一段，交接丢的东西最后是你买单。所以默认不拆，是省钱省时间，不是偷懒。

第 2 课 · 新默认：一个主循环，按需加载 Skill（对应 02 节）

文章给出的新默认：只留一个主 Agent 干全程，Skill 和工具平时只露个名字，用到的时候再加载全文。

对应知识点

  • 主循环（main agent loop）：一个人（一个模型）从头干到尾的工作方式。不换手，就没有交接成本。
  • 循环四步：写计划 → 调工具 → 看结果 → 修计划。一直转，直到给出答案，或者撞上预算停下。这是全文的骨架，记住这四步，就记住了单 Agent 是什么。
  • Skill（技能包）：写好的做事经验。像菜谱：步骤、规则、判断标准。注意：Skill 不是工具，是“怎么做事”的知识。
  • 工具：动手的东西：查资料、跑代码、发消息、读写文件。Skill 告诉它怎么做，工具让它能动手。一个是脑子里的经验，一个是手里的家伙。
  • 渐进披露（progressive disclosure）：平时只给目录，需要哪页翻哪页。就像平时只带一本薄薄的工具目录，真要拧螺丝了再去仓库提货。省的就是上下文那个台面。

第 3 课 · 为什么现在才行：三个变化（对应 03 节）

以前非拆不可，是因为模型太弱；现在不用拆了，是因为三个条件凑齐了。

对应知识点

  • 共享上下文不断裂：一个人从头看到尾，不用靠别人交回来的摘要过日子。写功能又写测试的如果是同一个人，上下文本来就在手里。
  • 系统提示词大瘦身：系统提示词就是开机时给模型的那份总指令。Skill 平时只露短说明，总指令就变薄了。Anthropic 说，靠这一招，它把 Claude Code 给新模型的系统提示砍了 80% 以上。
  • 模型硬实力跨代：从 Opus 4.5 起，模型能在单个循环里管更复杂的计划。以前那种僵硬的多 Agent 结构，反而会挡住新模型多干活。

第 4 课 · 单循环长什么样（对应 04 节）

这一节是全文的操作图。一个模型、一个上下文窗口，跑一个开放式工具循环。

目标 → 写计划 → 工具调用 → harness 交回原始结果 → 修订计划 → 答案（或撞上预算停下）→ verifier 核查

对应知识点

  • Harness（运行框架）：跑腿的架子。负责把工具调用真的跑起来、并行跑完、把原始结果交回来。它不决策，只执行。是执行层，不是大脑。
  • 预算：回合数 + 成本上限。撞上就停，不无限跑下去。这是防止 Agent 一根筋烧钱的安全绳。
  • Verifier（验证者）：只核对、不决策的检查员。像质检员：不参与做菜，只尝味道对不对。核对单号和日期对不对，但不决定怎么回答。
  • 三分法（分工不是按人头分，是按东西的性质分）：
    当“手脚”用的——要动手、要读实时数据、要返回固定格式结果的，放进工具。
    当“做事经验”用的——要知道“这个团队是怎么做事的”，也就是步骤、规则和判断的，放进 Skill。
    当“字典”用的——偶尔才查的参考资料，比如政策、指标定义、产品说明，放进知识库，需要时用搜索工具去查。
  • Anthropic 明确反对的做法：用代码把上下文抓出来、直接塞进提示词里。正确做法是让模型自己在循环里按需取。

第 5 课 · 工具太多，Agent 也会选错（对应 05 节）

工具不是越多越好。工具一多，模型挑花眼，选错的概率就上去了。

对应知识点

  • 工具定义：告诉模型“有这么个工具、怎么用”的说明书。工具越多，说明书越厚，模型越容易挑错。
  • 工程水位线：大约 30 到 50 个工具定义，选工具的准确率就容易下滑。这是文章给的经验数字，不是物理定律。
  • 工具搜索（tool search）：工具平时不全加载，Agent 按需发现、按需加载。解法不是按部门拆 Agent，而是工具按用户意图分组 + 按需搜索。
  • 例子与口径（注意，别当成通用承诺）：Anthropic 文档里的例子——GitHub、Slack、Sentry、Grafana、Splunk 这套常见组合，工具定义大约占 55,000 个 token，用工具搜索通常能砍掉 85% 以上。换一个团队未必是这个数。
  • Skill 库管理：Skill 会越长越大。文章的建议是：每个团队指定一个人管自己的 Skill，Skill 发布时自带评测；中央小团队统一管系统提示和整体质量。小团队反而迭代更快。

第 6 课 · Subagent 什么时候留 + 合并三步（对应 05 节后半 + 06 节）

Subagent 不是没用了，是从“默认选项”退居成了“特种部队”。只有特殊情况才派出去。

对应知识点

  • 三条硬标尺（至少踩中一条才加 Subagent）：
    ① 单 Agent 因为上下文膨胀，性能出现可测量的下滑——注意，是“可测量”，不是“感觉变差”。
    ② 几个任务可以并行跑，各自用完即弃的新上下文窗口。
    ③ 单 Agent 老选错工具，或者系统提示里有互相冲突的指令。
    三条之外先不加。
  • 两种常见留法（上面三条的展开，不是新标准）：
    并行只读的侦察工作：同时查几路资料、跑几项独立检查，派出去、收回来就好。
    验证工作：让一个独立 Agent 只跑测试、只报结果，不碰决策。
  • Eval（评测）：考试卷。黄金例题就是精心挑的考题，起步大约 10 道。没有考试卷，就不知道改完是变好还是变坏。
  • 基线：改之前先量的分数。没有基线，改完分数动了也不知道是进步还是退步。
  • 合并三步：先量、再合、后验。
    先量：每条在生产里会一起跑的 Agent 链都要有一道题，每条绝不能破的规则也要有一道题。
    再合：一次只改一处。两处一起改，分数动了不知道是谁动的。目标不是“全合掉”，保留本身就是合格结果，要的是“有证据的系统”。
    后验：看哪些题翻了，还要多跑几遍。工具包例子里的教训：一次合并降了延迟，却弄坏了一个原本正常工作的流程，而且这个故障在两次运行里只出现了一次。
  • Tamberwick Home：工具包自带的例子。起步是一个路由器加六个 Subagent，附带 19 道端到端评测题，还有不用 API key 就能先跑通流程的离线冒烟检查（基础排雷测试：先确认流程本身通不通，再谈对不对）。
  • 迁移工具包：Anthropic 在 GitHub 上线的参考实现，开源协议 Apache-2.0（拿去用可以），不接受外部维护（出了问题自己负责验证和维护）。工具包对每个 Subagent 会给一个裁决：合进主循环、和别的合并、改成工具调用，或者保留——裁决要自己复核，别当成官方背书。

第 7 课 · 外部佐证怎么读（对应 07 节）

除了 Anthropic 自己的实测，文章还引用了两条第三方观察。关键是：方向一致，不等于定论。

对应知识点

  • Vals 的研究（研究结论）：Agent 团队可以比单 Agent 更快，但质量并没有更高；从 10 个 Agent 扩到 30 个、100 个，质量没有提升，成本却明显更高。
  • Eric Provencher 的判断（个人判断）：他质疑 Agent 群的价值，称它们“几乎肯定”是在浪费钱。这是个人判断，不是研究结论。
  • 怎么读佐证：一个是研究结论，一个是个人判断，口径不同。两条和 Anthropic 的方向一致，但都不能直接当成“单 Agent 永远赢”的证据。以后看到“某某也这么说”，先问一句：这是研究、实测，还是个人判断？

第 8 课 · 一个任务，两种走法：客服问单号那次（对应 08 节）

拿工具包自带的例子走一遍，差别立刻看得见。用户问：我的订单到哪了，什么时候送到？

对应知识点

  • 多 Agent 的走法：路由器先接单，再交给订单 Agent 查单，订单 Agent 再把结果交给配送 Agent 查日期，最后汇总回主 Agent 回答。每次交接都是一次摘要，摘要里丢掉的东西，回答里就找不回来了。
  • 单循环的走法：主循环先加载订单 Skill，订单查询工具和配送查询工具都在手里，一次看完单号和日期再回答。只留一个独立的 verifier，核对单号和日期对不对，不碰决策。
  • 翻车教训：工具包的例子里有一次，主循环直接用订单工具自己回答了，没去问配送日期。教训不是“别合”，而是把“必须查配送日期”写进核查门里，而不是再加回一个 Agent。意思是：缺的东西，补到检查清单里，不补一个新人。

第 9 课 · 判断：默认不是信仰 + 一人公司打法（对应 09 节）

这一节的三句话是文章作者的判断，不是 Anthropic 的原话。判断和事实要分开，这是读所有文章都该有的习惯。

对应知识点

  • 判断一：默认单循环，因为交接成本是确定的，分工收益是不确定的。分工要先证明它省了什么，再谈它值多少钱。
  • 判断二：一人公司的场景里，三条保留标准其实常只剩两条在天天发生：验证者和并行侦察。权限隔离等到接外部不可信输入、或者 Agent 能写钱写库的时候再加，别提前搭一座空城。
  • 判断三（动手前三问，答不上来就先别合）：
    这一步能不能写成 Skill？
    有没有一道题能验它？
    合完之后，主循环会不会先回答、后核查？
  • 三个数字摆在一起看：评估改造成果时，永远把评测通过率、单任务成本、延迟三个数字摆在一起看。只盯速度，一定会把系统性的隐蔽故障藏起来。
  • 一人公司打法：先定一个主循环，再把重复做法写成 Skill，每个 Skill 配几道自己的黄金例题，合之前先测、合之后再测。你自己就是 Skill 库的唯一主理人，守住边界，别让它悄悄长成新的科学怪人提示词。
  • 护城河：你的护城河从来不是画出来的 Agent 数量，而是你手头每一个经过真实评测锤炼的 Skill。

第 10 课 · 这篇的边界：先说清楚，再下结论（对应 10 节）

好文章的一个标志：结论之前，先把自己的边界说清楚。这节就是边界。

对应知识点

  • 边界一：Anthropic 的结论来自企业部署经验，不是同行评审论文。经验很值钱，但不是论文级别的证明。
  • 边界二：跨客户的基准表没有公布，“快一倍”只是一个客户的对比，不能直接当成普适定律。
  • 边界三：迁移工具包有明确标注的未验证范围：完整单循环、Subagent 的合并与维护阶段、从没有评测的系统迁移、以及用到示例之外的系统，都不在已验证范围内；其中一部分改进只经过离线测试确认。
  • 边界四：工具包的裁决要自己复核，别把它当成官方背书。

记住这个习惯：以后你读任何一篇“某某指南说”的文章，先翻到它的边界节。没有边界节的文章，结论要打折听。

自测三问

不用写下来，能用自己的话答出来就算过。

  1. 循环四步是什么？
    写计划 → 调工具 → 看结果 → 修计划，直到给答案或撞上预算。
  2. Skill 和工具的区别是什么？
    Skill 是做事经验（菜谱：步骤、规则、判断），工具是动手的能力（手：查资料、跑代码、发消息）。
  3. 什么时候留 Subagent？
    三条硬标尺至少中一条：上下文膨胀导致性能可测量下滑；可并行、各用完即弃的新窗口；老选错工具或指令互相冲突。
